# POSFOXGEN

Run this workflow in the calling Harness. The Harness reads, debates, generates images and reviews visual evidence; Python only extracts, validates, edits, renders and records files. Do not invoke upstream model/API runners or request model API keys. No SAM is needed. If an image tool is unavailable, leave generation pending. A flattened bitmap is not an editable poster.

Use `scripts/run.py` from this skill's resolved directory with Python containing PyMuPDF and Pillow. It locates the accompanying project when symlinked. Read [workflow](references/workflow.md), [source geometry and visual fidelity](references/visual-fidelity.md), [prompt rules](references/prompt-rules.md) and the project's `references/poster-quality-research.md`. Model phases always run in the Harness. Start the poster's own clock after any workflow development/setup; keep per-stage timestamps and report actual elapsed wall time.

1. **Direct PDF ingestion and parallel preparation.** Use the user's supplied paper PDF directly. Parse the document normally and extract a useful inventory of complete figures/tables with captions and source locations; preserve readable axes, labels and legends. Record PDF point size, cropped pixel size, aspect ratio and source hash; carry these measurements and intended display frames into the generation prompt, not merely the extraction report. Keep the existing evidence-grounded crop method; no new selection-specific image-processing pipeline, arbitrary subfigure slicing, SAM3 or fixed half-image crops. Retain necessary crop correction/supplementation. Run independent PDF text parsing, figure extraction, user-reference reading and cached-rubric loading concurrently, then freeze the shared debate packet. Do not redownload a supplied paper or repeat the research survey.
2. **Parallel reports, then brief callback debate.** Keep necessary source supplementation, batching independent work concurrently. Freeze a shared PDF/source-image/reference/initial-plan packet and dispatch content advocate, science reviewer and visual planner together. Each may write one thorough initial report. Then allow one short callback debate round only on unresolved disagreements or consequential proposed changes; return issue IDs, positions, decisive evidence and a recommendation, not another full report or full-packet reread. Every role applies three lenses: rigor; protect what already works; and why not, testing the strongest case for both changing and retaining the original. The main executor resolves the short debate and applies accepted edits once. Reuse science-review evidence rather than adding a reviewer cycle. Preserve actual input snapshots, participant statements and main-executor resolutions; no fabricated approval. Follow workflow.md for schema and truthful bindings, then validate_content_debate and check-logic. Unresolved material faults remain explicit instead of extending debate.
3. **User reference first.** If the user identifies a main reference/template, use it as the primary design reference and attach it to the image-generation handoff; other supplied references are secondary. If the user supplies one reference without a rank, treat it as primary unless context says otherwise. A supplied scientific paper PDF remains the content/evidence source; a PDF explicitly supplied as a template has the reference role. Do not substitute another poster or launch a reference/palette search when the user already supplied the reference. Use the cached quality rubric and ordinary available fonts. Without a user reference, use the established local reference-selection method.
4. **Complete image generation.** Generation is built into this workflow; follow the local [generation brief](references/prompt-rules.md#fixed-generation-brief) and [generation handoff](references/workflow.md#content-debate-and-generation-handoff). Do not install or invoke a separate generation-only Skill. Assemble short fixed rules, substantive module copy, exact values/relations and full visual instructions. Pass `validate_generation_handoff` before the Harness image call. Every planned source figure/table must actually be drawn in the generated poster, including its contents. No blank frame, placeholder, reserved-for-later figure or figure-name-only substitute is acceptable. A five-attachment limit does not relax this. Generate one initial image and allow at most one regeneration (two image-generation calls total). Do not run a standalone generated-image review agent or review round. The reconstruction executor reads the generated design as part of normal reconstruction intake, records actual slot completeness and blockers with review_mode:"reconstruction_intake", its real reviewer name and independent:false, and proceeds directly to reconstruction. Do not claim an independent image review occurred. Keep the existing image_reviewed receipt for compatibility, with real image/plan hashes and observations. If a global fault requires regeneration, use the single retry; unresolved faults after it remain explicitly blocked rather than triggering more generation calls. Interrupted work remains pending; scores never override blockers.
5. **Single-response reconstruction.** Follow the editable reconstruction approach in [FigFox](https://github.com/LawrenceRiver/FigFox). Give one reconstruction model invocation the generated design, approved copy, complete source assets and short reconstruction prompt in references/reconstruction-prompt.md. Request complete editable HTML/SVG in one response, with visual alignment and all text inside its frames. Use the current Harness model, not an upstream API runner or a new model service/API-key setup. No SAM3, fixed 1/2 crops, separate planning-model invocation, trajectory optimizer or bespoke per-poster renderer development. Save the code and deterministically render it; model intake and reconstruction happen in the same invocation. During that intake, freeze and receipt-bind the actual generated-design roster before native construction: every module, area/text proportion, section/background color, bullet/dot/rule and source slot. Preserve repeated visual modules too; do not remove them as semantic duplicates. Reuse existing exporters and produce any required object/source metadata in the same response or by deterministic extraction, not a separate reasoning stage. Images keep aspect ratio and native size when possible; only uniformly shrink when needed. Use real source evidence, exact copy and native editable text/rules/tables. Follow with the bounded window revision protocol below.
6. **Bounded G1/G2 window revision.** Follow [window revision](references/window-revision.md). Freeze a repair budget before revision (default two G2 batches, hard maximum three; one batch for the baseline experiment). G1 checks every frozen module, repeated occurrence and local relationship using context and detail windows. G2 repairs only confirmed issues. Every batch requires a fresh render and G1 verification of original missing parts, neighbours and previously correct modules. Final review must inspect the actual final image; stale evidence cannot be rebound as a new observation. Stop on a complete pass, exhausted budget or no progress; unresolved faults remain blocked. No redesign, optional polish or FigFox code changes.

7. **Delivery.** Retain the best valid version, finalize only after logic, complete-image, reconstruction-fidelity, render and package reviews. Verify actual HTML/SVG/PNG/PDF bytes. Keep concise provenance, initial reports/callbacks, issue map, any actual repair and stage timing inspectable. New CLI runs use posfoxgen-v3 to enforce measured generation geometry and the intake-frozen design roster; v1/v2 runs remain historical. Local Harness judgments are not official PosterBench execution, and one pilot does not establish performance or stable latency.
