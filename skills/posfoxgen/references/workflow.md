# Local execution

The project root is the resolved skill directory's grandparent (`skills/posfoxgen`). Run all model actions in the current Harness. Existing local Python in this environment is `/opt/anaconda3/bin/python`; elsewhere use Python 3.10+ with the project's declared dependencies.

```sh
python skills/posfoxgen/scripts/run.py init --run runs/example --paper /absolute/paper.pdf --split development
python skills/posfoxgen/scripts/run.py assets /absolute/paper.pdf --out runs/example/source
python skills/posfoxgen/scripts/run.py check-logic --assets runs/example/source/asset_table.json --logic runs/example/logic_plan.json --panels runs/example/panel_plan.json --review runs/example/logic_review.json --out runs/example/logic_check.json
python skills/posfoxgen/scripts/run.py editable runs/example/poster_spec.json --assets runs/example/source/asset_table.json --out runs/example/editable
python skills/posfoxgen/scripts/run.py render runs/example/editable/poster.html --out runs/example/rendered
python skills/posfoxgen/scripts/run.py status --run runs/example
python skills/posfoxgen/scripts/run.py validate-delivery --run runs/example
```

`run.py --help` lists the workflow commands and routed `assets`, `editable`, and `render` tools. Use `run.py COMMAND --help` for that command's options.

## Independent logic review

Use the science participant's initial report plus its brief callback position, if any, as the independent logic-review evidence; do not dispatch a fourth reviewer or request another full-paper review. Its output must name actual checked claims/relations and source evidence, and give exact proposed wording for material corrections. Preserve the snapshot it actually reviewed. The main executor applies and verifies corrections, records its own resolution, and runs check-logic. Never impersonate a reviewer or claim it reread an amended plan. Review hashes must refer to actual inspected inputs; any mechanical binding of an assembled final plan must explicitly retain the original review snapshot and distinguish main-executor resolution from independent source review. If the existing gate cannot truthfully accept the evidence, leave it pending rather than inventing a second review or fabricating approval.

If separate agents are unavailable, disclose same-executor role passes and their weaker independence. Do not silently claim three-agent assurance.

## Content debate and generation handoff

Poster-image generation is part of this workflow. Use the local [fixed generation brief and per-module instructions](prompt-rules.md), then continue to the reconstruction handoff below. No separate generation package or remote generation instructions are required.

Retain necessary source-material supplementation: improve incomplete/unclear crops, source locations or missing figure context. Batch independent extraction, reference reading and source checks concurrently. Finish changes that affect scientific evidence before freezing the shared debate input; record a remaining nonblocking asset task separately rather than repeatedly changing inputs while reviewers read.

Freeze one shared packet: the supplied PDF, complete source crops, selected poster reference, source inventory, and the initial technical_story/content/logic/panel/figure-selection plans. Dispatch exactly three participants together: content advocate, science reviewer and visual planner. They inspect the same version independently, in parallel, each initially in one pass and each returning one substantial initial report. They can call read/view/search tools as needed within that pass. Do not request rewritten reports or full-packet rereads. After all initial reports return, permit one brief callback round on the explicit disputed issue IDs and any relevant proposed replacement text/source excerpts. Record that narrow callback scope separately; do not change the original shared packet or claim the whole amended plan was rereviewed.

The initial report may be thorough and long when evidence warrants it. Speak directly: name the missing/wrong item, cite the page/figure/source ID, give the exact change and its consequence. Avoid repeated paper summaries, praise and generic design advice. The callback must only highlight disputed points; never regenerate the long report. Report real issues only; do not pad a quota. For each material issue use issue_id, topic, target, evidence, consequence, proposed_change and blocking. If no issue is found, say so once. Include a compact checked-topics record with source IDs; collective positions/decisions cover all seven story topics plus logic, but every participant need not write all eight. Record actual reading/viewing scope; access to a file is not proof it was read.

Use the existing content_debate schema: participants [{role,reviewer,independent:true,positions,blockers}], decisions [{topic,resolution,source_ids}], blockers. The main executor merges duplicate findings, applies concrete accepted changes once, records declined changes briefly, and verifies the affected content against cited sources. Keep original participant opinions immutable; an issue's later resolution is the main executor's resolution, not an invented second participant output. Generation cannot proceed with unresolved material blockers. Materials supplementation remains permitted; the single long-report round and short callback remove repeated full reviews, not needed evidence collection.

After independent logic approval, save `generation_handoff.json` with `paper_source` copied exactly from the asset table, `user_requirements`, `technical_story`, `debate`, `content_plan`, `image_slots`, the expanded prompt and actual attachment paths. Content items are `{id,panel_id,role:'background'|'method'|'evidence'|'limitations',text,source_ids,typography_role:'body',requirement_ids:[]}`. Each planned image slot must have `{id,panel_id,source_ids,render_mode:'draw_full_source',instruction}`. `validate_generation_handoff(asset_table,panel_plan,handoff,requirements)` from `posfoxgen.generation_contract` checks that all slots are instructed to be drawn, no placeholder instruction contradicts this, scientific content roles and user qualifiers remain, and the debate is resolved. It cannot judge eventual pixels.

Use at most five existing local image attachments, or fewer if required by the image tool, with explicit roles (structural reference, colour source, scientific sources). For any unattached planned visual, supply its full labels, relations and values in the prompt. Attachment limits never justify a blank or reserved figure. The image model must draw every planned visual completely. Generate one initial image and allow at most one regeneration (two image-generation calls total). Do not run a standalone generated-image review agent or review round. The reconstruction executor reads the generated design as part of normal reconstruction intake, records actual slot completeness and blockers with review_mode:"reconstruction_intake", its real reviewer name and independent:false, and proceeds directly to reconstruction. Do not claim an independent image review occurred. Keep the existing image_reviewed receipt for compatibility, with real image/plan hashes and observations. If a global fault requires regeneration, use the single retry; unresolved faults after it remain explicitly blocked rather than triggering more generation calls.

Keep `source_replacements` as a map from each generated visual to its original evidence and intended geometry, not permission to leave generated visuals empty. In reconstruction, exact original assets or a source-checked native table replace generated approximations while matching the actual generated design. The generated figure and final scientific figure must have a documented semantic correspondence.

## Reconstruction fidelity

Stage reference: [FigFox](https://github.com/LawrenceRiver/FigFox) provides the editable reconstruction and scoped native-repair approach. Model work stays in the current Harness; the optional local bridge uses the pinned deterministic edit engine.

First map the actual generated design to `reconstruction_manifest.json`. Each panel supplies `reference_evidence:{path,region:[x,y,width,height],assessment}`, `style:{background,alignment,decoration_lines:[object IDs]}` and all intended `objects`. Record each object's rectangle, alignment and `near_background`, plus explicit text typography, source IDs and image-slot correspondence. Preserve rules and font styles. Native tables are preferred when they recreate the intended wide integrated table without stretching text. Images must never be stretched independently along either axis. Keep native size when it fits; only shrink uniformly when necessary to fit. The exporter uses scale-down and SVG preserves aspect ratio. Adjust the container, whitespace or layout instead of deforming the image. Legacy allow_distortion and distortion_reason cannot waive this rule. Scaling is enforced mechanically; do not add a separate visual inspection or reviewer round for scaling. Existing scientific/content and overall design reviews retain their own scope. Never crop a source to hide a fitting failure.

Bind `generated_image_path/generated_image_sha256` and `render_path/render_sha256` to actual viewed files. Call `validate_reconstruction_audit(panel_plan,manifest,exported_spec,review)` from `posfoxgen.reconstruction_audit`. The review needs `reviewer,independent:true,decision:'pass',checked_panel_ids,checked_object_ids,whole_poster_checked:true,findings,blockers:[]`, canonical `input_hashes` of `panel_plan,manifest,exported_spec`, and `evidence:{generated_image,rendered_image,actually_viewed:true}`. The machine checks actual exported object coverage and declarations; only the separate visual review can approve visual fidelity. Include header/footer as reviewed panels too.

Run `python -m posfoxgen.fonts` to inspect available families. `font_policy.require_available:true` prevents silently unavailable fonts. Use actual family-specific wrapping in HTML/SVG. System fonts remain local unless embedding is explicitly authorized and font restrictions permit it. For reusable distribution prefer a documented available family or licensed open font rather than copying a proprietary system file.

## File contracts

- `asset_table.json`: extractor-owned `root`, `source` (paper hash/path), `pages` (page text and preview), `assets` with `id,type,page,bbox,text/path,caption,source:{page,locator},sha256`. Source crop requests are `[{id,type:'figure'|'table',page,bbox:[x0,y0,x1,y1],caption,source_locator}]`, one-based page and PDF-point bounds. Crop only after inspecting the actual page. Set inspected crops' `render_scale:4` (or another justified value) for high-resolution PDF rendering; check actual pixel dimensions at display size.
- `logic_plan.json`: `planner`, `main_message`, `claims:[{id,text,evidence_asset_ids,qualifiers}]`, `relations:[{id,source,target,type}]`.
- `panel_plan.json`: `panels:[{id,title,purpose,claim_ids,asset_ids,reading_order,image_slots}]`. Reading order is unique. Every planned claim appears in a panel.
- `logic_review.json`: distinct `reviewer`, `independent:true`, `decision:'pass'|'blocked'`, all `checked_claim_ids` and `checked_relation_ids`, `findings`, and `evidence_notes:[{claim_id,source_locator,assessment}]`. Required `input_hashes` are the canonical JSON hashes returned by `validate_logic`; a missing or stale binding blocks approval. Independence requires a separate review pass that reads the evidence, not renaming the planner.
- `image_review.json`: `reviewer,decision,findings,blockers,input_hashes`. Bind exact file SHA-256 values for `image`, `logic_plan`, and `panel_plan`. Unresolved global semantic findings use `repairable:false`; local replacement/typographic findings may use `repairable:true`, with exact next actions. Protected sources do not become true because a generated diagram looks plausible.
- `poster_spec.json`: `title,width,height,background,panels:[{id,x,y,width,height,title,background?,objects:[]}]`. Coordinates are pixels; object coordinates are local to the panel. Text: `{id,type:'text',x,y,width,height,text,font_size,font_weight?,color?,font_family?,line_height?,source_ids:[]}`. Image: `{id,type:'image',x,y,width,height,asset_id,fit:'contain'}`. Tables use native `rows`, `column_widths`, `row_heights`, font, fill/header_fill, stroke and source IDs; line/rect objects preserve structural rules. See module docstrings/tests for exact optional fields. SVG geometry: `{id,type:'svg',x,y,width,height,svg,source_ids:[]}`. Text can declare `emphasis:[{text:"54.99",font_weight:700}]` for exact inline bold matches; HTML spans and SVG tspans preserve one editable paragraph and share real regular/bold width measurement. Every object ID is unique; source assets must hash-match. Use `export_svg` from `posfoxgen.editable` for native SVG.
- `quality_review.json`: named `reviewer`, inspected `evidence`, explicit `blockers`, and exactly seven `dimensions` each with `score` (0–100) and evidence-backed `reason`: faithfulness, coverage, density, visual_evidence, layout, readability, aesthetics. Aggregate via `posfoxgen.quality.assess`. Weights 10/10/15/10/20/25/10; protocol is local Harness assessment, not official PosterBench.
- `repair` records: issues, concrete plan/strategy, actual execution trajectory, before/after score, validity, applicability. `posfoxgen.memory` handles storage, retrieval, expected rewards and seeded exploration. `posfoxgen.figfox_bridge.apply_native_plan` executes real FigFox G1/G2 scoped transactions on native SVG without a model service.

## Stage receipts

Treat `editable` output as draft by default. Deterministic extraction, editable-file building and rendering may prepare drafts while review is pending; they do not advance the run or bypass approval. File existence is not acceptance. Only the required stage receipts and a passing final `validate-delivery` establish accepted delivery.

Accept stages in order: `assets`, `planned`, `logic_approved`, `image_reviewed`, `reconstructed`, optionally `repairing`, then `finalized`. With no effective issues in the complete G1 visual issue map, go directly from `reconstructed` to `finalized`. Use `accept-stage --run RUN --stage STAGE --artifact NAME=PATH` and `--review REVIEW.json` where required; relative artifact paths are relative to RUN. Assets use the name `asset_table`; planned uses `logic_plan` and `panel_plan`; logic uses `logic_review`. Final artifacts use names `poster_html`, `poster_svg`, `poster_png`, `poster_pdf`, `manifest`, `render_report`, and `quality_assessment`. Final review binds file SHA-256 values for `poster_html`, `poster_svg`, `poster_png`, `poster_pdf`, `render_report`, `logic_plan`, and `panel_plan`. Do not bind the manifest inside this review because the manifest itself binds the review. Finalization re-runs actual package validation and checks real render and quality reports; filenames alone never establish success. Accepting an earlier stage invalidates later ones. `status` invalidates receipts whose bound files or source changed. Never overwrite an accepted upstream artifact without re-reviewing downstream consequences.

## One visual issue map, conditional repair

After native reconstruction, make one source/generated-versus-native paired-window comparison, grouped by semantic regions (header, methods, evidence, results), not a fixed half-image split. Use the bounded G1/G2 protocol in [window-revision.md](window-revision.md); share each actual inspection across fidelity and final records for that same render. Preserve context, aspect and a common comparison scale. Window cropping is a deterministic operation, not a model stage.

Write visual_issue_map.json as a concise list of candidate issues. An effective issue must identify: a concrete observed defect; paired evidence paths and window coordinates; exact native object IDs; the relevant approved design/source requirement; the visible or reading/scientific consequence; a scoped repair action; and certainty. Mere stylistic alternatives, a vague score improvement, uncertain observations, or a difference with no material consequence do not authorize edits. Retain their dismissal reason briefly, without generating a repair plan. A confirmed scientific/content defect or real overflow remains material even if the rest of the poster looks good.

If there are no effective issues, proceed reconstructed → finalized directly using the inspected original reconstruction. Do not create an empty repair transaction, a fake repairing receipt, a reward report or a mandatory trajectory-optimization cycle. Existing actual-file/export checks remain applicable; passing means no material unresolved defect was observed, not that an unperformed inspection passed.

If effective issues exist, freeze that round's issue list and execute a scoped G2 batch. Follow [window-revision.md](window-revision.md) for the predeclared budget, mandatory post-repair G1, missing-part closure and regression checks. Never reuse an earlier render's observations as final evidence.


## Brief callback debate and shared reasoning lenses

After the three parallel initial reports, the main executor merges duplicates and sends only genuinely disputed or consequential items back once. Uncontested findings do not need a callback. The callback packet includes issue ID, original passage/design worth preserving, proposed change, exact source excerpt, and the disagreement to settle. Each invited participant responds briefly per disputed item: position (change/retain/conditional), decisive evidence, risk, and recommended exact action. Usually one to three sentences per item are sufficient; do not pad a quota, repeat the initial report, or reread every plan. This is one bounded debate round, not an open-ended chain. The main executor records the resolution and applies it; unresolved scientific ambiguity stays explicit rather than being decided by majority vote or a fabricated pass.

All three participants use all three lenses, not one lens assigned to each role:
- **Rigor:** Does the claim/change follow the actual paper, numbers, conditions and visual evidence? Distinguish a confirmed defect from uncertainty or preference.
- **Protect what works:** Name the original strengths and constraints a change must preserve. Prefer the smallest sufficient edit; do not damage accurate content, useful evidence, hierarchy or readability to improve a different attribute.
- **Why not:** Test the strongest reason to make the change and the strongest reason to retain the original. Ask what concrete benefit justifies editing, and what evidence would reverse the recommendation. Challenge both needless intervention and unexamined refusal to improve. This is not an invitation to brainstorm unrelated alternatives.

Keep participant initial reports and callbacks as separate immutable records. The main executor's synthesis/resolution does not count as another participant report and must not be attributed to one.


## Direct input and single-response reconstruction (latest user workflow)

Use the supplied PDF, keep normal source parsing/cropping and necessary supplementation, and parallelize independent input preparation. Do not add a custom processing stage for a particular selected image region. A user-designated main template is the primary reference passed to the generator; do not replace it with a searched template. A sole supplied reference defaults to primary. Treat paper PDFs as evidence and template PDFs as references according to their stated role. Reuse cached evaluation knowledge; no repeat survey when the inputs are provided.

Reconstruction is one model response containing complete editable HTML/SVG, guided by [the short prompt](reconstruction-prompt.md). It uses the calling Harness's model capability, without an upstream FigFox API runner, API key request, SAM3, fixed half-image crops, or an extra planning/strategy phase. Visual alignment and text containment are the two focal layout requirements. Preserve full scientific source content and image aspect ratio. Reuse deterministic export/render tools; do not develop a per-poster renderer. Produce the required source/object contracts alongside the artifact, not through another long model report. A response count is a workflow budget, not a measured latency guarantee.

Then follow the bounded G1/G2 protocol in [window-revision.md](window-revision.md). No effective issue means direct delivery after complete G1 coverage; otherwise repair and verify within the declared budget. This supersedes older one-map/one-batch wording.
